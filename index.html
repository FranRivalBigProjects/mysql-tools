MySQL Query Optimization Guide

1. Profile before optimizing

Never optimize blind. Enable the slow query log: slow_query_log = ON, long_query_time = 1. Use EXPLAIN to see the execution plan. Use SHOW PROFILE to see time per phase. The AI optimizer above automatically identifies the bottleneck category — full scan, filesort, bad join — and targets the highest-impact fix first.

2. The index hierarchy

  • Primary key: Clustered index — always O(log n), zero overhead
  • Covering index: All query columns in one index — no table lookup needed (Extra: Using index)
  • Composite index: Column order matters — most selective first, then range column last
  • Partial index (MySQL 8.0+): Index on expression for computed columns
  • FULLTEXT: For LIKE '%text%' patterns — replaces leading wildcard scans

3. Most impactful rewrites

  • N+1 subquery → JOIN: Scalar subquery in SELECT list runs once per row
  • IN (subquery) → EXISTS or JOIN: Correlated subqueries re-execute per row
  • OFFSET pagination → Keyset: Replace LIMIT x OFFSET y with WHERE id > last_seen_id
  • YEAR(col) → range: Replace function on column with BETWEEN '2026-01-01' AND '2026-12-31'
  • SELECT * → explicit columns: Enables covering indexes, reduces network transfer

4. InnoDB tuning baselines

  • innodb_buffer_pool_size: Set to 60–80% of available RAM — the most impactful MySQL config
  • innodb_io_capacity: Match to your disk IOPS (SSD: 2000+, NVMe: 10000+)
  • innodb_flush_log_at_trx_commit: 2 for most workloads (1 = fully durable but slower)
  • max_connections: Keep low — MySQL threads are heavy. Use connection pooling (PgBouncer port or ProxySQL)
  • query_cache_type: Disable in MySQL 8.0+ (removed) — use application-level caching instead

MySQL Query Optimizer – FAQ

How does this MySQL query optimizer tool work?

You paste your SQL query and optionally your CREATE TABLE schema. The AI analyzes the query structure — JOIN types, WHERE clause columns, ORDER BY, subqueries, and GROUP BY — against the schema to identify missing indexes, structural antipatterns (N+1, leading wildcards, functions on indexed columns), and rewrite opportunities. It returns a specific rewritten query, precise index creation statements, and an explanation of each change. Unlike rule-based linters, it understands query intent and proposes semantically equivalent rewrites.

Do I need to provide the schema (CREATE TABLE)?

Schema is optional but strongly recommended. Without it, the optimizer can only analyze query structure (N+1 patterns, wildcard usage, SELECT *, etc.). With schema, it can see existing indexes, column data types, cardinality hints, and foreign keys — enabling precise index recommendations like ALTER TABLE orders ADD INDEX idx_status_created (status, created_at); instead of generic advice.

What is the difference between this tool and Aiven SQL Query Optimizer?

Aiven's optimizer requires you to run a metadata query on your actual database server to collect statistics, paste the output into their tool, and have an Aiven account. This tool requires nothing — paste SQL and get results immediately. The tradeoff: Aiven's optimizer uses real table statistics (row counts, cardinality) for more precise recommendations on very large or unusual datasets. This tool uses schema-based analysis which covers 95% of common optimization cases without needing database access.

How do I use MySQL EXPLAIN to find slow query issues?

Prepend EXPLAIN to your SELECT: EXPLAIN SELECT * FROM orders WHERE status = 'pending';. Check the type column — ALL means full table scan (bad). Check Extra — Using filesort or Using temporary are warning signs. Check rows — high estimated row counts relative to actual results indicate poor index usage. Use EXPLAIN FORMAT=JSON for more detail, or EXPLAIN ANALYZE in MySQL 8.0+ for actual execution statistics.

What MySQL query patterns cause the worst performance?

Ranked by frequency and impact: (1) Missing index on JOIN or WHERE column — causes full table scan on every query. (2) N+1 subquery in SELECT list — executes once per result row. (3) LIKE '%keyword%' leading wildcard — no B-tree index can be used. (4) ORDER BY with no matching index — causes filesort. (5) LIMIT x OFFSET y deep pagination — scans all rows up to the offset. (6) SELECT * preventing covering indexes. (7) Functions on indexed columns in WHERE: WHERE YEAR(created_at) = 2026.
